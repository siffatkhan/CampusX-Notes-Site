3. Text Representation

One-Hot Encoding · Bag of Words · N-grams · TF-IDF · Using pretrained embedding models

NLP

Why Converting Text to Numbers Is Hard

Machine learning models only understand numbers — everything (text, images, audio) must eventually become numeric.

Images → Easy. Each pixel is already a number (brightness/intensity). An image is literally already a matrix of numbers.
Audio → Easy. Audio is a wave — a microphone records amplitude values over time: 0.12, 0.45, -0.30, 0.18, … Already a sequence of numbers.
Text → Hard. "I love pizza" → a computer sees 'I' 'love' 'pizza' — letters/symbols, not numbers, with no obvious numeric meaning.

Why specifically text is hard: words carry meaning, context, synonyms, spelling variations, and grammar. "Car," "automobile," and "vehicle" mean nearly the same thing — but as raw characters, a computer has no way to know that. This is why NLP relies on feature extraction techniques — instead of assigning arbitrary numbers to words, we use techniques that try to preserve meaning or importance: One-Hot Encoding, Bag of Words, N-grams, TF-IDF, and — covered in chapter 4 — Word2Vec, GloVe, FastText, and BERT embeddings.

Analogy: an image is like a paint-by-numbers grid — the numbers were already there. Text is like handing someone a poem in a language they've never seen — you have to build an entire translation system from scratch to give the symbols numeric meaning.

Key Terminology

📚 Corpus = the entire book (all pages combined). 📄 Document = one page. 🔤 Word/Token = one word on a page. 📖 Vocabulary = the unique dictionary of all words used, no duplicates. Important: corpus counts every occurrence (with repeats); vocabulary counts each unique word once — most text representation techniques build a vector whose length equals the vocabulary size, not the corpus size.

NLP

1. One-Hot Encoding

Every word is converted into a vector of length V (V = vocabulary size). The vector is all zeros, except a single 1 at the position corresponding to that word.

Vocabulary: [I, love, pizza, is, delicious, burgers] → V = 6 I → [1, 0, 0, 0, 0, 0] love → [0, 1, 0, 0, 0, 0] pizza → [0, 0, 1, 0, 0, 0] delicious → [0, 0, 0, 0, 1, 0]

Pros

Very intuitive, extremely easy to implement.

Cons

  • Sparsity — vectors are mostly zeros, wasteful in memory and computation.
  • No fixed input size — every sentence becomes a different number of vectors, causing problems for models expecting fixed-size input.
  • Out-of-Vocabulary (OOV) — a new word never seen during training has no valid representation.
  • No semantic meaning — "happy" and "joy" are just as "different" mathematically as "happy" and "table." Not used in practice anymore.
NLP

2. Bag of Words (BoW)

Core idea: ignore grammar and word order entirely. What matters is which words appear and how often (frequency) they appear in a document. Each document becomes one vector of length V, where each position holds the count of that vocabulary word in the document.

Doc1: "I love pizza" Doc2: "I love burgers" Vocabulary: [I, love, pizza, burgers] Doc1 → [1, 1, 1, 0] Doc2 → [1, 1, 0, 1] 
from sklearn.feature_extraction.text import CountVectorizer

cv = CountVectorizer()
X = cv.fit_transform(df['text'])

This solves the OOV problem partially — unseen words are simply ignored (not counted) rather than crashing the model; the vector stays valid, just doesn't reflect the unseen word.

Pros

  • Simple, intuitive
  • Fixed-size input — every document → a vector of length V regardless of sentence length
  • Documents with similar word usage end up with somewhat close vector directions → captures a small amount of semantic similarity

Cons

  • Still sparse for large vocabularies
  • OOV words are dropped (information loss)
  • Word order discarded — "food was good, not bad" and "food was bad, not good" can produce nearly identical BoW vectors despite opposite meaning
NLP

3. N-grams

Instead of treating single words (unigrams) as vocabulary items, group N consecutive words together as one "unit," to partially recover the word-order/context information that BoW throws away.

N=1 (unigram, regular BoW)
I, love, pizza
N=2 (bigram)
I love, love pizza
N=3 (trigram)
I love pizza
cv = CountVectorizer(ngram_range=(2, 2))   # bigrams only
X = cv.fit_transform(df['text'])

ngram_range=(2,2) shifts CountVectorizer from unigram-based BoW to bigram-based BoW.

Why this helps

"food was good not bad" → bigrams: [food was, was good, good not, not bad]. "food was bad not good" → bigrams: [food was, was bad, bad not, not good]. Now the two vectors look noticeably different (most bigram values differ), whereas plain unigram BoW would have made them look nearly identical — this is the key advantage of N-grams.

Pros

Makes semantically different sentences produce clearly different vectors; captures some word-order/context information BoW misses entirely.

Cons

Dimensionality increases rapidly as N grows (many more possible word-combinations than single words) → more sparsity, more memory/compute. Still no solution for unseen n-grams.

NLP

4. TF-IDF (Term Frequency – Inverse Document Frequency)

Not all words are equally important. TF-IDF assigns a higher weight to a word that appears frequently in one specific document but rarely across the rest of the corpus — because such a word is likely more distinctive/informative about that document's content. Common words that appear everywhere ("the," "is") get low weight, since they don't help distinguish documents.

Analogy: reading restaurant reviews, the word "food" appears in almost every review — it tells you nothing special. But "undercooked" appearing in only one review out of a thousand is a strong, distinctive signal about that specific review. TF-IDF mathematically rewards rare-but-locally-frequent words like "undercooked," and downweights generic words like "food."

Term Frequency (TF)

How frequently a term appears within one document. Always between 0 and 1; higher TF → word is prominent within that specific document.

$$ TF(t, d) = \frac{\text{number of times term } t \text{ appears in document } d}{\text{total number of terms in document } d} $$

Inverse Document Frequency (IDF)

How rare or common a term is across the whole corpus. If a term appears in almost every document → IDF is low (close to 0). If it appears in very few documents → IDF is high.

$$ IDF(t) = \log\left(\frac{\text{total number of documents in corpus}}{\text{number of documents containing term } t}\right) $$

TF-IDF Score

$$ TF\text{-}IDF(t, d) = TF(t, d) \times IDF(t) $$

Computed for every word in every document — the final vector for a document holds the TF-IDF score of each vocabulary word.

Worked Example — "pizza" vs "delicious"

Corpus (3 documents): Doc1 "I love pizza" · Doc2 "Pizza is delicious" · Doc3 "I love burgers"

"pizza" — appears in Doc1 and Doc2 (2 of 3 docs). TF in Doc1 = 1/3. IDF("pizza") = log(3/2) ≈ 0.176 (moderate, somewhat common). TF-IDF(pizza, Doc1) = (1/3) × 0.176 ≈ 0.059.

"delicious" — appears only in Doc2 (1 of 3 docs, rarer → more distinctive). TF in Doc2 = 1/3. IDF("delicious") = log(3/1) ≈ 0.477 (much higher, rare). TF-IDF(delicious, Doc2) = (1/3) × 0.477 ≈ 0.159.

Even though "pizza" and "delicious" both appear once in their respective document, "delicious" gets a higher score because it's rarer across the corpus — making it more distinctive/informative.

from sklearn.feature_extraction.text import TfidfVectorizer

tfidf = TfidfVectorizer()
X = tfidf.fit_transform(df['text'])

Pros

Gives meaningful weight to distinctive/informative words instead of treating all words equally (unlike plain BoW); automatically downweights very common, low-information words.

Cons

Still sparse, still no OOV support, dimensionality still tied to vocabulary size — and still no true semantic meaning: like BoW/N-grams, TF-IDF has no notion that "happy" and "joy" mean similar things; it only reflects statistical frequency/rarity.

The common thread: none of these frequency-based methods truly understand meaning — they're all fundamentally counting/weighting mechanisms. This is exactly the gap Word2Vec, GloVe, FastText, and BERT (prediction-based / contextual methods, chapter 4) are designed to close.

NLP

Using a Pretrained Embedding Model

Word2Vec/GloVe/FastText's training process (covered in full in chapter 4) works like this: take a massive corpus (e.g. all of Google News, ~100 billion words), run the training algorithm on it, and once training finishes you have a giant lookup table — every word that appeared in that corpus now has a fixed-length vector (e.g. 300 numbers) assigned to it. That lookup table — literally millions of word → vector pairs — is what gets saved to a file and released publicly as a "pretrained model."

Analogy: think of it like a massive, pre-built bilingual dictionary. Someone spent years compiling it (that's the "training"). You don't need to relearn Spanish yourself — you just open the dictionary and look up the word. Using a pretrained embedding model is exactly this: you look up a word, and it hands you back its vector.
import gensim.downloader as api

# downloads and loads Google's pretrained Word2Vec (trained on Google News)
model = api.load('word2vec-google-news-300')

# just LOOK UP the vector — no training, instant retrieval
vector = model['king']
print(vector.shape)   # (300,) → 300 numbers representing "king"

# use cosine similarity to find related words
print(model.most_similar('king'))
# [('queen', 0.65), ('monarch', 0.61), ('prince', 0.59), ...]

# famous analogy example: king - man + woman ≈ queen
print(model.most_similar(positive=['king', 'woman'], negative=['man']))

This is the most common way people "use" Word2Vec/GloVe — you never train anything yourself; you borrow vectors already computed on a corpus far bigger than what you could ever train on your own. Practical benefit: if a sentiment classifier's test set contains "fantastic" but the training data never had that word, a pretrained embedding for "fantastic" (close to "amazing"/"great") still lets the model make a sensible decision.

Applying This to Each Famous Model

GloVe (Stanford) — downloaded as plain text files (e.g. glove.6B.300d.txt); each line is a word followed by 300 numbers.

embeddings_index = {}
with open('glove.6B.300d.txt', encoding='utf8') as f:
    for line in f:
        values = line.split()
        word = values[0]
        vector = np.asarray(values[1:], dtype='float32')
        embeddings_index[word] = vector

print(embeddings_index['pizza'])   # → 300-dim vector

FastText (Facebook) — same lookup idea, but if a word is missing (OOV), FastText constructs a vector on the fly using character n-grams instead of failing.

import fasttext.util
fasttext.util.download_model('en', if_exists='ignore')
ft = fasttext.load_model('cc.en.300.bin')

print(ft.get_word_vector('dragonfruit'))  # works even if "dragonfruit"
                                           # wasn't in training data!

BERT embeddings (Google) — key difference: this breaks the "simple lookup table" idea. BERT is not a static dictionary; it's a full neural network you run text through every time, because the vector for a word depends on the surrounding sentence (contextual).

from transformers import BertTokenizer, BertModel
import torch

tokenizer = BertTokenizer.from_pretrained('bert-base-uncased')
model = BertModel.from_pretrained('bert-base-uncased')

text = "I deposited money in the bank"
inputs = tokenizer(text, return_tensors='pt')
outputs = model(**inputs)   # actual forward pass through the network — not a lookup!

# vector for "bank" here will differ from "bank" in "river bank"
word_vectors = outputs.last_hidden_state

ELMo — same idea as BERT: a trained bidirectional LSTM you run text through to get contextual vectors, rather than a static lookup table.

A pretrained model's vectors can also be loaded directly as the starting weights of your own network's embedding layer — a form of transfer learning, exactly like reusing a pretrained CNN's convolutional base for images (covered in the chapter 4 CBOW/skip-gram deep dive).

The One Sentence to Remember

  • Word2Vec / GloVe / FastText = pretrained lookup tables — static, one fixed vector per word, computed once, reused forever.
  • BERT / ELMo = pretrained networks — dynamic, a fresh, context-aware vector computed on each run.

In both cases, "using a pretrained model" means reusing knowledge someone else already extracted from massive data, so you don't need your own huge dataset or compute power — exactly the transfer-learning philosophy from computer vision.

Hard

5 questions on Text Representation. Pick an answer for each, then check.

1. Two reviews — "food was good, not bad" and "food was bad, not good" — end up with nearly identical Bag-of-Words vectors despite opposite meaning. What's the underlying cause, and what technique partially fixes it?

Explanation: BoW ignores order entirely, so these sentences (same words, different order) look nearly identical. Bigrams like "was good" vs "was bad" and "not bad" vs "not good" make the two vectors noticeably different — this is the core motivation for N-grams.

2. In a 3-document corpus, "delicious" appears in only 1 document while "pizza" appears in 2. Both appear once in their respective document (same TF). Which gets the higher TF-IDF score, and why?

Explanation: Per the worked example, IDF("delicious") = log(3/1) ≈ 0.477 vs IDF("pizza") = log(3/2) ≈ 0.176. With equal TF, "delicious" ends up with the higher TF-IDF score (≈0.159 vs ≈0.059) because rarity across the corpus makes it more distinctive.

3. Which statement is true of One-Hot Encoding, Bag of Words, N-grams, and TF-IDF as a group?

Explanation: The summary table's "common thread": none of these frequency-based methods truly understand meaning — they're all counting/weighting mechanisms. This is exactly the gap prediction-based methods like Word2Vec are designed to close.

4. What is the key structural difference between using a pretrained Word2Vec/GloVe model and using pretrained BERT embeddings?

Explanation: Word2Vec/GloVe/FastText are static lookup tables — "bank" always gets the same vector. BERT computes a fresh vector from an actual forward pass every time, so "bank" in "river bank" differs from "bank" in "bank account."

5. Why does One-Hot Encoding fail to represent a sentence as fixed-size input, while Bag of Words solves this?

Explanation: One-Hot gives each individual word its own V-length vector, so a longer sentence produces more vectors — no fixed size. BoW instead produces one V-length count-vector per document, which is the same length no matter how long the document is.
