6. Named Entity Recognition (NER)

Finding & classifying real-world entities in text · spaCy's doc.ents · Lookup vs rule-based vs ML-based approaches

NLP

What Is NER?

Named Entity Recognition is the task of finding and classifying "named entities" in text — real-world objects like people, organizations, locations, dates, money amounts, products, etc. — and labeling what type of entity each one is.

Sentence: "Elon Musk founded SpaceX in California in 2002." Elon Musk → PERSON SpaceX → ORG (organization) California → GPE (geo-political entity / location) 2002 → DATE
Analogy: reading a sentence normally, you see just a stream of words. NER is like using a highlighter with different colors — one for people's names, another for places, another for dates — so you can instantly scan and pull out exactly the "who, where, when" facts from a wall of text.

NER builds directly on POS tagging (chapter 5) — POS tagging tells you a word is a noun/proper noun, but NER goes a step further and tells you what kind of real-world thing that noun refers to.

Why NER Matters — Use Cases

Search Engines / News Search

Searching "Elon Musk news" needs the engine to recognize "Elon Musk" as a specific person entity, not just three separate common words, so it retrieves articles specifically about him.

Recommendations

Reading several articles mentioning "Tesla" and "SpaceX" (ORG entities) lets a recommendation system detect the pattern and suggest more content involving those organizations — beyond just keyword matching.

Customer Care / Support Chatbots

"My order #48213 from Amazon hasn't arrived since March 5th" — NER can automatically pull out the order number, organization, and date, letting the system route or auto-fill a support ticket without manual re-typing.

Analogy: NER is an assistant that reads a huge pile of documents for you and pulls out sticky notes labeled "Person," "Company," "Date," "Money" — so you never have to read the whole document to find the key facts.
NLP

Using spaCy for NER

import spacy
nlp = spacy.load("en_core_web_sm")

doc = nlp("Elon Musk founded SpaceX in California in 2002.")

for ent in doc.ents:
    print(ent.text, ent.label_)

# Output:
# Elon Musk   PERSON
# SpaceX      ORG
# California  GPE
# 2002        DATE

doc.ents holds the entities spaCy found in the text; ent.text is the entity's text span and ent.label_ is its predicted entity type.

Visualizing with displaCy

from spacy import displacy
displacy.render(doc, style="ent")

This highlights entities directly in colored boxes over the text — much easier to scan visually than reading raw label output.

NLP

Approaches to Building NER Systems

1. Simple Lookup (Dictionary-Based)

Maintain a predefined list ("gazetteer") of known entities — e.g. all country names, all known company names — and check if a word/phrase matches something in that list. If the list contains ["USA", "India", "Germany"], any exact match gets tagged as a location.

Pros: extremely simple, fast, no training needed. Cons: can't handle new/unseen entities not in the list, and can't use context — it will incorrectly tag "Turkey" as a country even in "I'm cooking turkey for dinner."

Analogy: a fixed phonebook — if a name isn't already written in the book, you have no way of recognizing it, no matter how obviously it looks like a name.

2. Rule-Based NER (Regex, Pattern Matching)

Define explicit patterns/rules to catch entities that follow a predictable structure. Dates: \d{1,2}/\d{1,2}/\d{4} catches "05/03/2024". Money: \$\d+(\.\d{2})? catches "$45.99". Capitalized word sequences right after "Mr./Dr./Mrs." → likely a PERSON name.

Pros: works very well for structured entities with predictable formats (dates, phone numbers, money, emails) — no training data needed. Cons: breaks easily on messy real-world text; can't detect entities without a clear structural pattern (e.g. "Zephyra Technologies" as a company name has no fixed regex to catch it).

Analogy: teaching someone "any word right after 'Mr.' is a person's name" — great for consistent formats, but falls apart the moment text doesn't follow the expected pattern.

3. Machine Learning-Based NER (CRF, BERT)

The modern, most accurate approach — a model learns from labeled examples what entities typically look like in context, instead of relying on hardcoded rules.

CRF (Conditional Random Fields) — a statistical sequence-labeling model, similar in spirit to HMM (chapter 5) but more flexible: it can incorporate many features at once (the word itself, its POS tag, surrounding words, capitalization, prefixes/suffixes) rather than just "previous tag → next tag." Learns from a labeled corpus which feature combinations mark entity boundaries and types — good for structured prediction where sequence matters (e.g. "New" + "York" together = one LOCATION entity, not two).

BERT-based NER — uses a pretrained transformer fine-tuned for entity recognition. Because BERT produces contextual embeddings (chapter 4), it can much better distinguish "Apple" the company vs. "apple" the fruit, or "Amazon" the company vs. "Amazon" the river, based on the surrounding sentence. Currently the state-of-the-art approach — significantly outperforms rule-based and CRF on messy, real-world text, because it generalizes to unseen entities via context/semantics rather than memorized patterns.

Pros: handles unseen entities well, understands context, robust to messy real-world text. Cons: requires labeled training data, more computationally expensive, less transparent/interpretable than simple rules.

Analogy: a lookup table is like memorizing a fixed list of celebrity names. Rule-based is like knowing "capitalized words after 'Mr.' are names." ML-based (BERT) is like a well-read, experienced person who can correctly identify that "Kai" is a person's name in one sentence and a brand name in another, purely by understanding sentence context.

5 questions on Named Entity Recognition. Pick an answer for each, then check.

1. A dictionary-based NER system tags "Turkey" as a LOCATION in the sentence "I'm cooking turkey for dinner." What's the root cause?

Explanation: This is the source's own example of simple lookup's key weakness: it matches text against a fixed list with no notion of context, so it can't distinguish "Turkey" the country from "turkey" the food regardless of list size.

2. Which approach can correctly distinguish "Apple" the company from "apple" the fruit purely by understanding the surrounding sentence, without ever having memorized that specific case?

Explanation: BERT-based NER uses contextual embeddings, so the same word gets a different vector depending on sentence context — exactly what's needed to tell "Apple" (ORG) apart from "apple" (fruit) without memorizing the specific case, unlike lookup or rule-based approaches.

3. What is the key advantage CRF has over a plain HMM-style approach for sequence labeling tasks like NER?

Explanation: CRF is similar in spirit to HMM (also a statistical sequence-labeling model) but more flexible — it isn't limited to "previous tag → next tag" transitions and can use many features simultaneously, which HMM's structure doesn't directly support.

4. In spaCy, which code correctly extracts each recognized entity's text and label from a processed document?

Explanation: doc.ents is spaCy's collection of recognized entities; each has .text (the entity span) and .label_ (its type, e.g. PERSON/ORG/GPE/DATE). token.pos_ is for POS tags, not entities.

5. Why does the notes' comparison table rate rule-based (regex) NER as unable to handle new/unseen entities, even though it needs no training data?

Explanation: Rule-based NER works great for structured formats (dates, money) but has no fixed pattern to catch an arbitrary company name like "Zephyra Technologies" — it breaks on messy or unpredictable real-world text precisely because it depends on explicit structural patterns.
