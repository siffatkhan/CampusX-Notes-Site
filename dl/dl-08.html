Day 15

MLP Memoization

"Memoization" is a general programming idea: instead of recomputing an expensive result every time you need it, compute it once and store ("remember") it, then reuse the stored value later. Applied to a multilayer perceptron (MLP), memoization is exactly what makes backpropagation efficient rather than absurdly expensive.

During the forward pass, every layer computes two things per neuron: the pre-activation \( z = w \cdot a_{prev} + b \) and the activation \( a = g(z) \). A naive implementation might discard these once it hands the final prediction to the loss function — but chapter 6's worked example showed that the backward pass needs exactly these intermediate values again. Computing \( \partial L/\partial w_1 \) required \( a_h \) (the hidden activation) and reused \( \partial L/\partial z_o \) (computed while finding \( \partial L/\partial w_o \)). Those aren't optional conveniences; without them, computing a single early-layer gradient would mean re-running large chunks of the forward pass from scratch, for every single weight, in every single layer.

Why the network "remembers" the forward pass: every framework (Keras/TensorFlow, PyTorch) caches each layer's inputs, pre-activations (z), and activations (a) as the forward pass runs, and builds a computation graph recording how each value was produced from the last. The backward pass then walks that graph in reverse, and at every node it needs a derivative, it looks up the already-cached forward value instead of recomputing it. This turns what would be an exponential-time computation (re-deriving every intermediate value fresh at every step) into a linear-time one — one forward pass, one backward pass, done.

Why this matters practically

  • Speed: without caching, training a network with L layers could require work that scales quadratically (or worse) with depth instead of linearly.
  • Memory trade-off: caching every layer's activations for every training example in a batch is exactly why deep networks are memory-hungry during training (and why techniques like gradient checkpointing exist — deliberately discarding some cached activations and recomputing them on demand to trade compute time for lower memory use).
  • It's invisible in practice: in Keras/TensorFlow or PyTorch, this caching happens automatically inside model.fit() / loss.backward() — you never manually store activations, but understanding that it's happening explains why forward and backward passes are always paired, and why you can't call .backward() usefully without having just run a forward pass on the same computation graph.
Day 16

Gradient Descent in Neural Networks

The ML track's Linear Regression chapter introduced Batch, Stochastic, and Mini-batch gradient descent as three ways of deciding how much data to use per weight update. Every one of those ideas carries over directly to neural network training — the only thing that changes is that "the weight" now means potentially millions of weights across many layers, all updated together via backpropagation on every step.

VariantRows per updateTrade-off in NN training
Batch GDEntire datasetVery stable gradient direction, but one update per epoch and the entire dataset (plus every cached activation) must fit in memory at once — usually infeasible for real datasets.
SGD1 rowExtremely fast, noisy updates that can help escape shallow local minima and saddle points — but the noise also makes convergence erratic, and GPU hardware is wasted processing one row at a time instead of in parallel.
Mini-batch GDA fixed batch size (e.g. 32, 64, 128, 256)The practical default: small enough to fit in memory and keep updates frequent, large enough to give a reasonably stable gradient estimate and let GPUs process the whole batch in parallel via matrix operations.

Batch size

A hyperparameter: how many training examples are processed together before one weight update.

Iteration

One forward pass + backward pass + weight update, using exactly one batch.

Epoch

One complete sweep through every batch — i.e. through the whole training set once.

Code — Choosing batch size in Keras

history = model.fit(
    X_train, y_train,
    batch_size=32,     # mini-batch GD — the practical default
    epochs=50,         # 50 full passes over the training data
    validation_split=0.2
)

# batch_size = len(X_train)  -> Batch GD (1 update per epoch)
# batch_size = 1             -> SGD (noisy, slow on GPU)
# batch_size = 32/64/128     -> Mini-batch GD (the usual choice)
Day 17

How to Improve the Performance of a Neural Network

There's no single fix that makes a struggling network perform well — improvement is a checklist, and the right item on it depends on which way the model is currently failing. The first step is always diagnosis before treatment.

Step 0 — Diagnose underfitting vs overfitting first

Compare training loss to validation loss. Both high → underfitting (the model isn't capturing the pattern at all — needs more capacity or better features). Training loss low but validation loss high and diverging → overfitting (the model has memorized training data — needs more data or more regularization). Applying an overfitting fix to an underfitting model (or vice versa) makes things worse, not better — always check this first.

More data / data augmentation — the single most reliable fix for overfitting. If collecting more labeled data isn't possible, augmentation (random crops/flips/rotations for images, synonym swaps for text, noise injection generally) manufactures more varied training examples from what you already have.
Better architecture — the right inductive bias beats brute-force capacity: CNNs for images, RNNs/Transformers for sequences. Also consider width and depth — too few neurons/layers underfits, too many (without regularization) invites overfitting.
Hyperparameter tuning — learning rate is usually the single highest-leverage number in the whole setup; also batch size, number of layers/neurons, and activation choice. Search this systematically (grid/random search, or Keras Tuner — see chapter 10) rather than by hand-guessing.
Regularization — L1/L2 weight penalties and dropout, both covered later in this chapter, directly target overfitting by constraining what the model is allowed to do with the training data.
A better optimizer — swapping plain SGD for Adam or RMSProp (chapter 10) often gets a model to a better minimum, faster, with less manual learning-rate babysitting.
Batch normalization — stabilizes and speeds up training by keeping layer inputs in a consistent range (chapter 10), and often lets you use a higher learning rate safely.
Transfer learning — start from a model already trained on a large, related dataset (e.g. ImageNet-pretrained CNNs) and fine-tune it on your smaller dataset, instead of training from random initialization.
Early stopping — a nearly free regularizer: stop training the moment validation performance stops improving, covered next.
Day 18

Early Stopping

Left to train indefinitely, a neural network's training loss keeps falling — but its validation loss typically falls, bottoms out, and then starts rising again as the model begins memorizing training-set noise instead of learning generalizable patterns. That validation-loss upturn is the visible signature of overfitting starting to take hold, and early stopping is simply the decision to stop training right around that turning point, rather than continuing on to a worse generalizing model.

Patience: validation loss is noisy epoch to epoch, so stopping the instant it ticks up even once would stop training prematurely. The patience parameter says "wait N epochs without improvement before actually stopping" — giving the model room for a temporary blip while still catching a genuine, sustained upward trend.

Early stopping is often called a "free" regularizer because, unlike L1/L2 penalties or dropout, it doesn't change the model architecture, the loss function, or add any computation to each training step — it only changes when you stop, using information (the validation curve) you were already computing anyway.

Code — Early Stopping with Keras

from tensorflow.keras.callbacks import EarlyStopping

early_stop = EarlyStopping(
    monitor='val_loss',       # watch validation loss
    patience=5,                # allow 5 epochs of no improvement before stopping
    restore_best_weights=True  # roll back to the best epoch's weights, not the last
)

history = model.fit(
    X_train, y_train,
    validation_split=0.2,
    epochs=200,                 # set generously high — early stopping decides the real end
    callbacks=[early_stop]
)

restore_best_weights=True matters: without it, training stops at the patience-triggered epoch, but the model's weights are left at that later, already-worse-than-best point rather than rolled back to the true minimum of the validation curve.

Day 19

Data Scaling in Neural Networks

The reasoning here is the same one gradient descent for Linear Regression relies on: when input features sit on wildly different scales (say, "age" in single digits next to "salary" in the hundreds of thousands), the loss surface becomes a long, narrow, stretched-out bowl rather than a nicely rounded one. Gradient descent zig-zags inefficiently across such a surface instead of heading straight for the minimum, and a learning rate that's stable for the small-scale feature can be wildly unstable for the large-scale one. Scaling every feature to a comparable range removes that distortion and lets a single learning rate work well for every weight at once.

For neural networks specifically, this matters even more than for linear regression, because the effect compounds across layers — an imbalanced input scale doesn't just slow convergence at the first layer, it feeds forward into every subsequent layer's activations too.

ScalerWhat it doesTypical use
StandardScalerTransforms each feature to zero mean, unit varianceDefault choice for most NN inputs
MinMaxScalerRescales each feature into a fixed range, usually [0, 1]Image pixel values (0–255 → 0–1), bounded features
 
from sklearn.preprocessing import StandardScaler

scaler = StandardScaler()
X_train_scaled = scaler.fit_transform(X_train)   # fit only on training data
X_test_scaled = scaler.transform(X_test)         # apply the SAME transform to test data

# never fit the scaler on test data — that would leak test-set
# statistics into training, inflating your evaluation
Scaling doesn't stop at the input layer. As data passes deeper into the network, each layer's own weights can re-introduce exactly this same scale problem to the next layer's input — which is precisely the problem batch normalization (chapter 10) solves: it re-standardizes activations inside the network, between layers, the same way a StandardScaler standardizes raw inputs before the network ever sees them.
Day 20

Dropout Layer

Dropout is a regularization technique aimed directly at overfitting: during each training step, a randomly chosen fraction of neurons in a layer are temporarily "dropped" — their output forced to zero, as if they didn't exist for that step. Which neurons get dropped is re-randomized on every batch, so the network can never rely on any particular fixed set of neurons always being available.

Why this prevents overfitting — breaking co-adaptation. Without dropout, neurons can develop brittle, over-specific co-dependencies — neuron A learns to only work correctly in combination with the exact outputs of neurons B and C, memorizing quirks of the training data rather than a generally useful feature. Because dropout can remove B or C at any moment, every neuron is forced to learn something that's independently useful, not just useful in one narrow, memorized combination. The net effect behaves like implicitly training a large ensemble of thinned sub-networks that share weights, and averaging their predictions.
The dropout rate — a hyperparameter (commonly 0.2–0.5) specifying the fraction of neurons zeroed out on each step. Higher rate → stronger regularization, but too high starves the network of enough active neurons to learn effectively.
Disabled at inference time — once training is done, every neuron is kept active for predictions (you want the full network's capacity when it actually matters). Frameworks automatically rescale the remaining activations during training to compensate, so the expected output magnitude matches between train and inference time without any manual adjustment.

Code — Dropout with Keras

from tensorflow.keras.models import Sequential
from tensorflow.keras.layers import Dense, Dropout

model = Sequential([
    Dense(128, activation='relu', input_shape=(20,)),
    Dropout(0.3),                      # zero out 30% of this layer's outputs, per batch
    Dense(64, activation='relu'),
    Dropout(0.3),
    Dense(1, activation='sigmoid')
])

# Dropout is active during model.fit() and automatically
# switched off during model.predict() / model.evaluate() —
# no manual toggling needed
Day 21

Regularization in Deep Learning

This is the exact same idea as Ridge (L2) and Lasso (L1) regression from the ML track — add a penalty term to the loss that discourages large weights — just applied to a neural network's (potentially millions of) weights instead of a handful of linear-regression coefficients.

$$ L_{total} = L_{original} \;+\; \underbrace{\lambda \sum_{j} w_j^2}_{\text{L2}} \quad\text{or}\quad L_{total} = L_{original} \;+\; \underbrace{\lambda \sum_{j} |w_j|}_{\text{L1}} $$
L2 (weight decay) — like Ridge, shrinks every weight smoothly toward (but not exactly to) zero. The dominant choice for regularizing NN weights, because it keeps every connection, just makes none of them dominant.
L1 — like Lasso, can drive individual weights to exactly zero, effectively pruning connections out of the network. Useful when a sparser, more compressed network is desirable.

Just as with Ridge/Lasso, \( \lambda \) controls the strength of the penalty: too small and it barely constrains overfitting; too large and it forces weights so close to zero the network can't learn the signal at all — the same bias-variance dial covered in the ML track's regularization chapter.

Code — L2 Regularization with Keras

from tensorflow.keras.layers import Dense
from tensorflow.keras.regularizers import l1, l2, l1_l2

model = Sequential([
    Dense(128, activation='relu', input_shape=(20,),
          kernel_regularizer=l2(0.001)),   # L2 penalty, lambda=0.001
    Dense(64, activation='relu',
          kernel_regularizer=l1_l2(l1=0.0005, l2=0.0005)),  # elastic-net style mix
    Dense(1, activation='sigmoid')
])

In practice, L2 weight decay, dropout, and early stopping are often combined — they attack overfitting through three different mechanisms (penalizing weight size, breaking co-adaptation, and limiting training time) and stack well together.

Test Your Understanding

Hard

5 questions on the Deep Network Training Toolkit. Pick an answer for each, then check.

1. Why do frameworks cache activations from the forward pass instead of recomputing them during backpropagation?

Explanation: The chain rule needs quantities like a neuron's activation or pre-activation to compute derivatives with respect to weights feeding into or out of it. Memoizing them during the forward pass avoids re-deriving those same values repeatedly, turning backprop into an efficient linear-time algorithm.

2. A dataset has 10,000 rows and batch_size=100. How many iterations occur per epoch, and which GD variant is this?

Explanation: 10,000 ÷ 100 = 100 iterations per epoch. Since the batch size (100) is neither 1 nor the full dataset (10,000), this is Mini-batch Gradient Descent.

3. Training loss is high AND validation loss is high, and both are close together. What should you try first?

Explanation: Both losses high and close together is the signature of underfitting — the model lacks capacity to fit even the training data well. Options B, C, and D all further restrict the model, which would make underfitting worse, not better.

4. Why is dropout disabled at inference (prediction) time?

Explanation: Dropout's randomness is a training-time regularizer that prevents co-adaptation. At prediction time you want the full, fully-trained network making the call — frameworks keep all neurons active and rescale automatically so magnitudes stay consistent with training.

5. What is the key structural difference between L1 and L2 regularization on a neural network's weights?

Explanation: This mirrors Ridge (L2) vs Lasso (L1) from the ML track exactly: L1's absolute-value penalty geometrically favors landing exactly on zero for some weights, while L2's squared penalty smoothly shrinks all weights without ever fully eliminating any of them.
