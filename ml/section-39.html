39. Handling Imbalanced Data

Why accuracy lies on skewed classes · undersampling & oversampling · SMOTE's synthetic interpolation · class_weight, and avoiding leakage

Extended notes — this topic isn't covered in the CampusX playlist notes this site is based on. Written from scratch to continue the curriculum, in the same style as the rest of the site.
Classification

The Problem — When Classes Aren't Balanced

Every classification example you've seen so far quietly assumed the classes show up in roughly similar numbers. Real data is rarely that polite. Fraud detection: maybe 0.1% of transactions are fraudulent. Disease screening: maybe 2% of patients actually have the rare condition. Manufacturing defect detection: maybe 1 in 10,000 parts is defective. These are imbalanced classification problems, and they break the naive way of training and evaluating models.

The 99% accuracy trap

Suppose 99% of transactions in your dataset are legitimate and 1% are fraud. A model that does nothing — that simply predicts "not fraud" for every single transaction, ignoring the input entirely — scores 99% accuracy. It also catches exactly zero fraud, which is the entire point of building the model in the first place. Accuracy is computed as (correct predictions) / (total predictions), and when one class dominates the total, a model can rack up a high score just by parroting the majority class, never learning anything about what makes the minority class distinct.

Why this connects back to the Confusion Matrix

The Classification Metrics page's confusion matrix explains exactly why this happens and how to see past it. The lazy "always predict majority" model gets true negatives on almost every row (correctly saying "not fraud" for the 99% that really aren't), zero true positives (it never once correctly flags actual fraud), and — critically — 100% false negatives on the class you actually care about catching. Metrics that ignore this imbalance (plain accuracy) look great; metrics computed specifically on the minority class — recall, precision, F1 — reveal the model is useless. This is exactly why the metrics page emphasized precision/recall/F1 over raw accuracy for skewed problems: they force you to look at how the model performs on the class that actually matters.

Beyond the evaluation problem, there's a training problem too: most learning algorithms are implicitly trying to minimize overall error across the whole training set. With 99 examples of one class for every 1 of another, the loss signal from the majority class dominates by sheer volume, and the model has very little incentive to learn the minority class's pattern at all — even if that pattern is perfectly learnable in principle. The rest of this page covers the standard toolkit for fixing this at the data level (resampling) and the algorithm level (class weighting).

Concept

Undersampling

The simplest fix: throw away majority-class rows until the classes are balanced (or closer to it). RandomUnderSampler does exactly this — it randomly removes majority-class samples until the class ratio you asked for is reached.

Upside

Fast, simple, and shrinks the dataset — useful when you have so much majority-class data that training on all of it is itself a computational burden.

Tradeoff — loses information

You're literally deleting real, potentially useful data. If the majority class has meaningful internal variety (several distinct sub-patterns), randomly discarding most of it can remove sub-patterns the model needed to see, hurting its ability to distinguish "hard" majority-class examples from the minority class.

Code — RandomUnderSampler

from imblearn.under_sampling import RandomUnderSampler
from collections import Counter

print("Before:", Counter(y_train))   # e.g. {0: 9900, 1: 100}

rus = RandomUnderSampler(sampling_strategy=0.5, random_state=1)  # minority:majority = 1:2 after
X_res, y_res = rus.fit_resample(X_train, y_train)

print("After:", Counter(y_res))      # e.g. {0: 200, 1: 100}
Concept

Oversampling

The mirror-image approach: instead of removing majority-class rows, duplicate minority-class rows until the classes are balanced. RandomOverSampler picks minority-class rows at random (with replacement) and copies them until the desired ratio is reached.

Upside

No data is thrown away — every original row, majority and minority, is still represented. Preserves all the information undersampling would have discarded.

Tradeoff — overfitting risk

Because the "new" minority rows are exact copies, the model can effectively memorize those specific points rather than learning the general pattern behind them. With enough duplication, a flexible model (like a deep Decision Tree or KNN with small K) can carve out decision boundaries that fit these repeated points suspiciously precisely — classic overfitting, just induced by duplication instead of by model complexity alone.

Code — RandomOverSampler

from imblearn.over_sampling import RandomOverSampler
from collections import Counter

print("Before:", Counter(y_train))   # e.g. {0: 9900, 1: 100}

ros = RandomOverSampler(sampling_strategy=1.0, random_state=1)  # fully balance 1:1
X_res, y_res = ros.fit_resample(X_train, y_train)

print("After:", Counter(y_res))      # e.g. {0: 9900, 1: 9900} -- minority rows duplicated
Concept

SMOTE — Synthetic Minority Oversampling Technique

SMOTE fixes oversampling's core weakness — exact duplication — with one clean idea: instead of copying an existing minority point, manufacture a brand-new synthetic point that lies between two real minority points that are already close together. The model then sees genuinely new (if artificial) data rather than repeated points.

The interpolation mechanic

  1. Pick a minority-class point, call it \(x\).
  2. Find its k-nearest minority-class neighbors (a small k, e.g. 5, is typical).
  3. Randomly pick one of those neighbors, call it \(x_{nn}\).
  4. Generate a new synthetic point somewhere on the straight line segment between \(x\) and \(x_{nn}\):
$$ x_{\text{new}} = x + \lambda \cdot (x_{nn} - x), \qquad \lambda \sim \text{Uniform}(0, 1) $$

λ is a random number between 0 and 1, so \(x_{new}\) lands at a random point somewhere between \(x\) and its neighbor — not on top of either one. Repeat this process (choosing a random minority point and a random one of its neighbors each time) until you've generated as many synthetic points as you need to reach your target balance.

Because each synthetic point sits in the local neighborhood of real minority points — where the minority class is known to actually exist — SMOTE effectively "fills in" the gaps between sparse minority observations, rather than stacking weight onto identical copies. This gives the model more varied minority-class examples to learn a genuine decision boundary from, instead of a boundary shaped around a few overrepresented exact points.

Illustrative aid — generated for this site.

Code — SMOTE

from imblearn.over_sampling import SMOTE
from collections import Counter

print("Before:", Counter(y_train))   # e.g. {0: 9900, 1: 100}

smote = SMOTE(k_neighbors=5, sampling_strategy=1.0, random_state=1)
X_res, y_res = smote.fit_resample(X_train, y_train)

print("After:", Counter(y_res))      # e.g. {0: 9900, 1: 9900} -- new synthetic points, not copies

SMOTE isn't magic — it only interpolates within the region already spanned by known minority points, so it can't invent an entirely new mode of the minority class that never appeared in training. It can also generate noisy synthetic points if minority-class points are themselves scattered near the majority class's region (a variant, Borderline-SMOTE, specifically targets points near the decision boundary to address this). Still, plain SMOTE is a strong, widely used default.

Concept

Practical Guidance — Avoiding Leakage

The single most important rule: resample ONLY the training set

Never apply undersampling, oversampling, or SMOTE to your validation or test set — and never resample before splitting into train/test. Your validation and test sets exist to estimate how the model will perform on real, naturally-imbalanced future data. If you balance them artificially, that estimate becomes meaningless — you'd be measuring performance on a distribution that will never actually occur in production.

There's a subtler leakage risk with SMOTE specifically: if you run SMOTE on the entire dataset before splitting, some synthetic training points can end up interpolated using neighbor information from points that later land in your test set — meaning your model was effectively trained using information derived from test data. Always split first, then resample the training portion only.

Doing this safely inside cross-validation

The same logic applies inside k-fold cross-validation: resampling must happen inside each fold's training portion, not once on the whole dataset before the folds are cut — otherwise synthetic/duplicated points derived from a row can leak into a different fold's validation split. imblearn provides its own Pipeline (distinct from sklearn's) specifically so that resampling steps are correctly refit fresh within each CV fold, using only that fold's training data.

from imblearn.pipeline import Pipeline   # NOTE: imblearn's Pipeline, not sklearn's
from imblearn.over_sampling import SMOTE
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import cross_val_score, StratifiedKFold

pipeline = Pipeline([
    ('smote', SMOTE(random_state=1)),          # applied fresh, inside each fold's training data only
    ('clf', RandomForestClassifier(random_state=1))
])

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=1)
scores = cross_val_score(pipeline, X_train, y_train, cv=cv, scoring='f1')
print("CV F1 scores:", scores)
print("Mean F1:", scores.mean())

# Final fit for deployment: fit the pipeline once on the full training set
pipeline.fit(X_train, y_train)
print("Test F1:", f1_score(y_test, pipeline.predict(X_test)))  # X_test/y_test never resampled

A resampling-free alternative — class_weight='balanced'

Many sklearn estimators (LogisticRegression, SVC, DecisionTreeClassifier, RandomForestClassifier, and others) accept a class_weight parameter. Setting class_weight='balanced' doesn't touch your data at all — instead, it automatically reweights the loss function so that misclassifying a minority-class example is penalized more heavily than misclassifying a majority-class one, roughly in inverse proportion to each class's frequency. This nudges the model to pay attention to the minority class without generating or deleting a single row, avoiding both undersampling's information loss and oversampling/SMOTE's added complexity and leakage surface.

from sklearn.linear_model import LogisticRegression

# No resampling at all -- the loss function itself compensates for imbalance
clf = LogisticRegression(class_weight='balanced', max_iter=1000)
clf.fit(X_train, y_train)   # trained directly on the original imbalanced data

A good rule of thumb: try class_weight='balanced' first — it's free, has zero leakage risk, and requires no extra library. Reach for SMOTE or explicit resampling when class_weight alone isn't enough, or for algorithms that don't expose a class_weight option at all.

Test Your Understanding

Hard

5 questions on Handling Imbalanced Data. Pick an answer for each, then check.

1. A dataset is 99.5% negative / 0.5% positive. A model that always predicts "negative" scores 99.5% accuracy. Why is this score misleading?

Explanation: Accuracy = correct / total, and with 99.5% of rows negative, predicting "negative" always gets nearly all of the total right by volume alone. But this model produces zero true positives and 100% false negatives on the class that matters — precision, recall, and F1 (from the Classification Metrics page) expose this failure, while accuracy hides it.

2. What is the key mechanical difference between RandomOverSampler and SMOTE when creating new minority-class rows?

Explanation: RandomOverSampler literally copies rows, which can encourage a model to overfit to those exact repeated points. SMOTE instead picks a minority point and one of its k-nearest minority neighbors, then generates a new point somewhere along the line segment between them (x_new = x + λ(x_nn − x), λ ∈ [0,1]) — a genuinely new, if synthetic, data point.

3. You apply SMOTE to your entire dataset (both what will become train and test rows) before doing train_test_split. What's wrong with this order of operations?

Explanation: Resampling (SMOTE especially) must happen only on the training portion, after splitting. Resampling before splitting both leaks neighbor information across the eventual train/test boundary and corrupts the test set's class distribution, making test performance no longer representative of real-world, naturally-imbalanced deployment data.

4. Why does imblearn provide its own Pipeline class instead of relying solely on sklearn's Pipeline when resampling is involved in cross-validation?

Explanation: sklearn's Pipeline doesn't support resampling steps that change the number of rows (its transformers must preserve row count). imblearn's Pipeline extends this so a resampler is correctly re-applied fresh to each fold's training split during cross_val_score/GridSearchCV, keeping validation folds free of leaked resampled information — the same reasoning as never resampling the held-out test set.

5. You want to address class imbalance without generating any synthetic rows or deleting any real ones, and your chosen algorithm supports it. What's the most direct option?

Explanation: class_weight='balanced' reweights the loss function to penalize minority-class errors more heavily, without touching the dataset at all — no rows added, none removed. The other three options (undersampling, oversampling, SMOTE) all modify the actual rows the model trains on.
