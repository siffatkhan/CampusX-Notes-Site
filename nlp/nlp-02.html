2. The NLP Pipeline & Text Preprocessing

Data acquisition → text preparation → feature engineering → modeling → deployment · Tokenization, stop words, stemming vs lemmatization, spaCy

NLP

The End-to-End NLP Pipeline

This pipeline is not universal — every real project bends it — and it is non-linear in practice (you loop back to earlier steps as you learn more). Deep learning pipelines look slightly different, mainly because feature engineering is largely automatic rather than a manual step.
1. Data Acquisition
↓
2. Text Preparation (cleanup → basic preprocessing → advanced preprocessing)
↓
3. Feature Engineering (BoW, TF-IDF, Word2Vec, …)
↓
4. Modeling (model building → evaluation)
↓
5. Deployment (deploy → monitoring → model update)

1. Data Acquisition

  • If data is available: from a database, a CSV/table, or via API / web scraping / PDF / images / audio.
  • If data is limited: apply data augmentation — e.g. bigram-based augmentation, back-translation, or adding noise/synonym replacement.
  • If no data exists at all: gather it directly via surveys, forms, or questionnaires.

2. Text Preparation

  • Text cleanup — removing HTML tags, encoding/removing emojis, spell checking.
  • Basic preprocessing — tokenization, stop-word removal, lower/upper-casing, stemming/lemmatization.
  • Advanced preprocessing — POS tagging, parsing (understanding sentence structure), coreference resolution.

3. Feature Engineering

Converting cleaned text into numbers: Bag of Words, TF-IDF, One-Hot Encoding, Word2Vec (chapters 3–4). Which technique to use depends on the problem. In classic ML this is done manually using domain knowledge; in deep learning, feature engineering happens automatically inside the network.

4. Modeling

Model building can follow the heuristic approach, a classic ML algorithm, deep learning (often via transfer learning — e.g. taking a BERT model already trained on huge data and applying it to your problem), or a cloud API. Which technique to use depends on data size and the nature of the problem. Evaluation is then split into: intrinsic evaluation (accuracy, confusion matrix — measured offline) and extrinsic evaluation (how the model performs after deployment, in an actual business setting).

5. Deployment

Deploy the model into production, then monitor it — checking from time to time how it's performing in the real world — and update it as needed (product changes, new data, drift, etc. — there are many possible reasons a model needs updating over time).

Perplexity is a metric that tells us how "confused" an NLP language model is at a given point — lower perplexity generally means the model is more confident/accurate about what word should come next.
NLP

Text Cleanup & Basic Preprocessing

Raw text is messy — inconsistent casing, HTML tags, URLs, punctuation, slang, typos, emojis. Before any text representation technique (BoW, TF-IDF, Word2Vec — chapters 3–4) can work well, we clean the text so the model focuses on meaningful words instead of noise.

Lowercasing

Convert all text to lowercase so "Pizza" and "pizza" aren't treated as two different words — without this, the vocabulary double-counts the same word in different cases, which wastes space and hurts pattern matching.

Removing HTML Tags & URLs

Text scraped from web pages or reviews often carries leftover markup (<br>, <p>) or URLs — neither carries semantic value for most NLP tasks, so both are stripped with regex. Tip: regex101.com is a handy tool for testing patterns interactively before using them in code.

Removing Punctuation

Punctuation (!, ,, .) usually adds no useful signal for classic text-representation techniques, so it's stripped out.

Chat-Word Treatment

Internet slang/abbreviations (lol → laughing out loud, lmao → laughing my ass off, wth → what the hell) are converted into their full form via a lookup dictionary, so the model can actually understand them.

Removing Short Words

Very short words (i, am, a) often carry little standalone meaning and are sometimes filtered out to reduce noise — similar reasoning to removing stopwords.

Spell Correction

Fixes typos ("pizzza" → "pizza") so misspelled variants aren't treated as unique, unrelated words. Commonly done with the TextBlob library.

from textblob import TextBlob

corrected = TextBlob("pizzza is amazingg").correct()

Handling Emojis

Two approaches: remove emojis entirely, or replace them with their textual meaning (preserves sentiment/information). Replacing is usually better than removing when sentiment matters — a 🔥 emoji carries real emotional signal that shouldn't just be thrown away.

import re

def remove_emoji(text):
    emoji_pattern = re.compile("["
        u"\U0001F600-\U0001F64F"  # emoticons
        u"\U0001F300-\U0001F5FF"  # symbols & pictographs
        u"\U0001F680-\U0001F6FF"  # transport & map symbols
        u"\U0001F1E0-\U0001F1FF"  # flags
        u"\U00002702-\U000027B0"
        u"\U000024C2-\U0001F251"
        "]+", flags=re.UNICODE)
    return emoji_pattern.sub(r'', text)

# Replacing emoji with meaning (better — preserves sentiment info)
import emoji
print(emoji.demojize('Python is 🔥'))
# Output: "Python is :fire:"
NLP

Tokenization

What it is: breaking text into smaller units — sentences into words, or words into characters — because models process language piece by piece, not as one giant blob of text. Why we do it: every text representation technique (BoW, TF-IDF, Word2Vec — chapters 3–4) operates on individual tokens, not whole sentences; tokenization is the mandatory first step that produces those units.

Naive ways

  • split() — splits on whitespace only; breaks on edge cases (e.g. "Mr. Smith" incorrectly splits at the period).
  • Splitting via regex — more control, but still limited.

Proper way

NLTK / spaCy — real NLP libraries that correctly handle punctuation, abbreviations, contractions, and other edge cases. spaCy is the most preferred library — faster, more robust, production-grade.

Efficiency tip: nlp.pipe()

Calling nlp() once per row (one document at a time) is slow. spaCy provides nlp.pipe(), which processes many texts in a batched, optimized way — much faster for large datasets.

import spacy
nlp = spacy.load("en_core_web_sm")

# Slow way — one call per document
docs = [nlp(text) for text in texts]

# Fast way — batched, optimized processing
docs = list(nlp.pipe(texts))
NLP

Removing Stop Words

Stopwords are extremely common words (the, is, my, a, and) that appear everywhere and carry little distinctive meaning. Removing them reduces vocabulary size and lets the model focus on meaningful/content words — commonly handled via NLTK's built-in stopword list.

Analogy: stopwords are like "um," "uh," "so" in spoken conversation — grammatically necessary for humans, but if you're trying to figure out what a conversation is about, you can safely ignore them.
When NOT to remove them: POS tagging needs the full sentence structure intact, including stop words — removing "is," "the," or "not" can destroy grammatical context a POS tagger relies on. Similarly, tasks where word order and function words carry meaning (parsing, some sentiment cases where "not" flips polarity, or any sequence model like an LSTM/Transformer that already handles frequency imbalance internally) often perform worse with stopwords stripped out. The rule of thumb: for frequency-based bag-style features (BoW/TF-IDF) feeding classic ML models, remove them; for tasks that depend on grammatical structure, keep them.
NLP

Stemming vs. Lemmatization

The problem both solve: words like "playing," "played," "plays," "player" all share the same root idea — "play" — but to a machine these are completely different strings, unnecessarily inflating vocabulary size.

Stemming

Chops off word endings using fixed rules to reduce a word to its stem — no grammar or dictionary knowledge involved, just pattern-based suffix removal. "Running" → "runn". Fast, but can produce non-words. Mostly used in information retrieval systems (search engines), where exact grammatical correctness doesn't matter, just matching similar words.

Analogy: a lawnmower — chops off anything sticking up past a certain length, without caring whether what's left still looks grammatically correct.

Lemmatization

Converts a word to its actual dictionary/base form — its lemma — using real vocabulary and grammar knowledge. "Running" → "run" (always a real English word). Internally it looks up words in WordNet, a lexical dictionary of relationships between English words, and you must specify the part of speech for accurate results (e.g. "better" as adjective → "good"). Slower, but accurate.

Analogy: a skilled gardener who knows exactly what each plant should look like and prunes it back to its proper natural form.

Types of Stemmers — Side-by-Side Comparison

Porter Stemmer (most common, English-only) — removes common suffixes: ing, ed, ly, es, s. "playing" → "play" ✅. "study" → "studi" — not a real word, but that's fine; Porter only cares that similar words map to the same stem, not that the output is valid English.

Lancaster Stemmer — "Porter's aggressive cousin," cuts much more. maximum → maxim, happiness → happy, running → run, organization → org, general → gen (loses meaningful information — too aggressive).

Snowball Stemmer (Porter2) — an improved, more refined Porter. studies → studi, playing → play, happiness → happi. Better linguistic rules, supports multiple languages, generally produces slightly better stems than Porter. Most practitioners prefer Snowball.

Regexp Stemmer — no linguistic intelligence at all; you manually define the rule, e.g. RegexpStemmer("ing$") removes "ing" only if it's at the end. playing → play, swimming → swimm, singer → singer (unchanged — doesn't end in "ing").

Worked example — "The children were running better than the adults."
Stemming: the children were run better than the adult (often can't handle irregular forms like "children" or "better").
Lemmatization: the child be run good than the adult — notice children → child, were → be, better → good. A stemmer typically cannot make these grammar-aware transformations.
When to use which:
No output shown to the user (internal processing, e.g. feeding a classifier's TF-IDF) → stemming — fast, and classic ML models (Naive Bayes, Logistic Regression, SVM) perform nearly as well on stemmed text.
Output IS shown to the user (chatbot replies, summaries, search snippets) → lemmatization — produces grammatically correct, readable real words.
Never chain them. You pick one, never both — each is already a complete transformation of the word. Stemming after lemmatization (or vice versa) can distort the text further and adds no benefit.

Test Your Understanding

Hard

5 questions on the NLP Pipeline & Text Preprocessing. Pick an answer for each, then check.

1. A team building a chatbot needs to know each word's grammatical role, so they run POS tagging as a preprocessing step. Should they remove stop words first?

Explanation: Stop-word removal is a task-dependent choice, not a universal step. For POS tagging, the full grammatical structure — including "is," "the," "not" — is needed, so stop words are kept, unlike for BoW/TF-IDF feature pipelines feeding classic ML models where removing them helps.

2. Which pair of outputs correctly matches "running" processed by (a) a stemmer and (b) a lemmatizer?

Explanation: Stemming crudely chops the ending using fixed rules and can produce a non-word like "runn." Lemmatization uses dictionary/grammar knowledge and always returns a real word — the actual lemma "run."

3. A search engine needs to match "studies," "studying," and "study" together quickly across millions of documents, with no need to show grammatically correct output to any user. What's the better choice, and why?

Explanation: The rule from the notes: when output isn't shown to a user (internal processing like information retrieval matching), use stemming — it's fast, and real-word correctness doesn't matter for matching similar terms.

4. Why does spaCy's nlp.pipe() outperform calling nlp() in a per-row loop over a large dataset?

Explanation: Calling nlp() once per row is slow; nlp.pipe() processes many texts in a batched, optimized way, which is much faster for large datasets — it still runs the full pipeline (tokenizer, tagger, etc.), just more efficiently.

5. In the end-to-end NLP pipeline, where does "coreference resolution" belong, and what category of preprocessing is it?

Explanation: The pipeline groups text preparation into basic preprocessing (tokenization, stop words) and advanced preprocessing (POS tagging, chunking, coreference resolution) — coreference resolution sits in the advanced tier since it requires deeper structural/semantic understanding.
